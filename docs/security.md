# Security

This document covers how dcdash protects its data, how users authenticate and what they
are allowed to do.

## Data at rest

dcdash keeps its state in an SQLite database, `<data_dir>/dcdash.db`. The data directory is
created with mode `0700` and the database file with mode `0600`.

Secrets that dcdash has to read back later, such as TOTP seeds, are additionally encrypted in
the database with **AES-256-GCM**:

- Each encrypted value carries a random nonce and the ID of the key that encrypted it.
- Each value is bound to its purpose with *associated data* (for example `totp:<user>`), so an
  encrypted value can't be moved to another field or user.
- Secrets that only need to be compared are **hashed instead**: recovery codes and session
  tokens are never stored in plain text or in a reversible form.

### The encryption key

```yaml
security:
  encryption_key: "file:/etc/dcdash/encryption.key"
```

Generate a key with `dcdash gen-key` (32 random bytes, base64-encoded) and store it outside the
configuration file, readable only by the dcdash user:

```sh
umask 077
dcdash gen-key > /etc/dcdash/encryption.key
chown dcdash: /etc/dcdash/encryption.key
```

**Back up the key separately from the database.** Without it, the encrypted secrets can't be
recovered. For TOTP this means every user has to enroll again after an administrator reset.

At the first start, dcdash stores a check value encrypted with the key. If dcdash is later
started with a different key, it refuses to start instead of failing on individual records:

```text
security.encryption_key does not match the database; if the key was changed,
list the old key in security.previous_encryption_keys
```

### Key rotation

Rotate the key when it may have been exposed, or according to your policy:

1. Generate a new key and make it the `encryption_key`. Move the old key to
   `previous_encryption_keys`:

   ```yaml
   security:
     encryption_key: "file:/etc/dcdash/encryption-2027.key"
     previous_encryption_keys:
       - "file:/etc/dcdash/encryption.key"
   ```

2. Restart dcdash. Data encrypted with the old key stays readable. Everything written from now
   on uses the new key, and the key check value is re-encrypted right away.
3. Re-encrypt the remaining data with the new key. Until a re-encryption command is available
   (it comes with the first encrypted data, TOTP in Sprint 4), records are re-encrypted when
   they are next written.
4. Once all data is re-encrypted, remove the old key from `previous_encryption_keys` and
   destroy it.

Several previous keys can be listed. Keys are identified by a fingerprint stored with each
value, so their order doesn't matter.

## Authentication

### LDAP

Users log in with their directory account (`auth.ldap`). dcdash searches the user with a
read-only service account, then binds as the user on a separate connection to verify the
password.

- **Transport:** `ldaps://`, or `ldap://` with `start_tls: true`. Plain `ldap://` requires
  `insecure: true` and is meant for tests only.
- **Server verification:** the system CAs plus `tls.ca_file`, or a pinned certificate
  fingerprint (`tls.fingerprint`, SHA-256). Pinning suits Samba's autogenerated certificate,
  which has no subject alternative name and therefore fails normal host name verification:

  ```sh
  openssl s_client -connect dc1.example.com:636 </dev/null | openssl x509 -noout -fingerprint -sha256
  ```

  Compare the fingerprint with the certificate on the domain controller
  (`/var/lib/samba/private/tls/cert.pem`) before trusting it. A pin has to be updated when the
  certificate is renewed.
- **Credential handling:**
  - Empty passwords never reach the directory, because LDAP treats them as an anonymous bind,
    which succeeds.
  - Login names are escaped before they're used in search filters.
  - Disabled AD accounts are rejected.
- **Groups:** in AD mode, nested groups are resolved with `LDAP_MATCHING_RULE_IN_CHAIN`. The
  primary group (usually "Domain Users") isn't a `member` relationship in AD, so it isn't
  reported; don't map roles to it.
- **Errors:** unknown users, wrong passwords and disabled accounts all return the same
  response ("invalid username or password").

### Sessions

- The browser receives a random 256-bit token in the cookie `__Host-dcdash_session`, which is
  `Secure`, `HttpOnly` and `SameSite=Strict`. The database stores only the token's SHA-256
  hash.
- A session ends after `auth.session.lifetime` (default 8 hours) or after `idle_timeout`
  (default 30 minutes) without requests, whichever comes first. Logging in again always
  creates a new session, so a session can't be fixed in advance (session fixation).
- When a session advances a step (password, then TOTP), its token is replaced.

### CSRF protection

State-changing requests must pass three checks:

1. An `Origin` (or `Referer`) header, if present, must match the requested host.
2. Request bodies must be JSON. Cross-site HTML forms can't send JSON without a CORS
   preflight, and dcdash never allows CORS.
3. With a session, the `X-CSRF-Token` header must contain the session's token. It is returned
   by login and `GET /api/v1/auth/me`.

The login request itself is exempt from check 3, because it replaces any existing session.

### Lockout

After `auth.lockout.user.max_failures` failed logins for a user name (default 5 in
15 minutes), or `auth.lockout.ip.max_failures` from one client IP address (default 20), further
attempts are refused with HTTP 429 for the lockout duration. Locked attempts don't reach the
directory, which also protects the AD accounts against the domain's own lockout policy. If
dcdash runs behind a reverse proxy, list the proxy in `server.trusted_proxies`. Otherwise all
clients share the proxy's address.

Lockout state is kept in memory and is reset when dcdash restarts.

### Break-glass account

If the directory is unavailable, nobody can log in via LDAP. For this case an optional local
account can be enabled:

```sh
dcdash hash-password > /etc/dcdash/breakglass.hash   # asks for the password (min. 16 characters)
```

```yaml
auth:
  local:
    enabled: true
    username: breakglass
    password_hash: "file:/etc/dcdash/breakglass.hash"
```

- The username is reserved: logins with this name are never sent to the directory. Choose a
  name that doesn't exist there.
- The password is stored as an argon2id hash (64 MiB memory, 3 iterations, 4 lanes).
- The account **always** has to complete the TOTP step. Its sessions can't be used before
  that. The TOTP step arrives in Sprint 4; until then, the account can't complete a login.
- Every use is logged as a warning. The account holds the `root` role (Sprint 4).

## Roles and permissions

Roles map directory groups to permissions:

```yaml
auth:
  root_group: dashroot          # default
roles:
  - name: dns-operator
    groups: ["dcdash-dns"]      # CN, or a full DN
    require_totp: true          # default
    permissions:
      - "dns:cloudflare-prod:*:write"
      - "dns:bind-internal:*:read"
```

A user holds every role whose groups they're a member of, including nested groups in AD
mode. Group names without `=` are compared with the group's CN. Values with `=` are compared
as DNs. Both comparisons ignore case.

### The root role

Members of `auth.root_group` hold the built-in `root` role. It has every permission
(`*:*:*:admin`) and always requires TOTP. A configured role can't be named `root`, so the
role can't be weakened or removed. The break-glass account always holds `root`.

### Permission format

A permission has four segments, `module:instance:resource:action`:

| Segment | Meaning | Examples |
|---|---|---|
| module | The service family | `proxmox`, `dns`, `dhcp`, `system` |
| instance | A configured backend, by name | `cluster-a`, `cloudflare-prod`; always `core` for `system` |
| resource | An object of the backend | a VM, a zone, a subnet; `audit` or `sessions` for `system` |
| action | The level of access | see below |

The resource may contain colons, for example an IPv6 subnet:
`dhcp:kea:2001:db8::/64:read`.

`*` matches any text, as a whole segment or within one: `dns:*:*.example.com:write` covers
`www.example.com` but not `example.com` itself. Matching is case-sensitive.

Actions are ordered, and a higher action includes all lower ones:

| Action | Allows |
|---|---|
| `read` | Viewing |
| `operate` | Operating without changing configuration, for example starting or stopping a VM |
| `console` | Interactive console access |
| `write` | Creating, changing and deleting |
| `admin` | Everything; `*` as the action means `admin` |

Permissions only grant; there are no deny rules.

### System permissions

| Permission | Allows |
|---|---|
| `system:core:audit:read` | Reading the audit log |
| `system:core:sessions:read` | Listing all sessions |
| `system:core:sessions:write` | Terminating other users' sessions |

Resetting another user's TOTP is reserved for `root`.
