# Security

This document covers how dcdash protects its data, how users authenticate and what they
are allowed to do.

## Data at rest

dcdash keeps its state in an SQLite database, `<data_dir>/dcdash.db`. The data directory is
created with mode `0700` and the database file with mode `0600`.

Secrets that dcdash has to read back later, such as TOTP seeds, are additionally encrypted in
the database with **AES-256-GCM**:

- Each encrypted value carries a random nonce and the ID of the key that encrypted it.
- Each value is bound to its purpose with *associated data* (for example `totp:<user>`), so an
  encrypted value can't be moved to another field or user.
- Secrets that only need to be compared are **hashed instead**: recovery codes and session
  tokens are never stored in plain text or in a reversible form.

### The encryption key

```yaml
security:
  encryption_key: "file:/etc/dcdash/encryption.key"
```

Generate a key with `dcdash gen-key` (32 random bytes, base64-encoded) and store it outside the
configuration file, readable only by the dcdash user:

```sh
umask 077
dcdash gen-key > /etc/dcdash/encryption.key
chown dcdash: /etc/dcdash/encryption.key
```

dcdash warns at startup if the configuration file or a file referenced with `file:` (keys,
tokens, passwords) is accessible by other users (any permission for "others").

**Back up the key separately from the database.** Without it, the encrypted secrets can't be
recovered. For TOTP this means every user has to enroll again after an administrator reset.

At the first start, dcdash stores a check value encrypted with the key. If dcdash is later
started with a different key, it refuses to start instead of failing on individual records:

```text
security.encryption_key does not match the database; if the key was changed,
list the old key in security.previous_encryption_keys
```

### Key rotation

Rotate the key when it may have been exposed, or according to your policy:

1. Generate a new key and make it the `encryption_key`. Move the old key to
   `previous_encryption_keys`:

   ```yaml
   security:
     encryption_key: "file:/etc/dcdash/encryption-2027.key"
     previous_encryption_keys:
       - "file:/etc/dcdash/encryption.key"
   ```

2. Restart dcdash. Data encrypted with the old key stays readable. Everything written from now
   on uses the new key, and the key check value is re-encrypted right away.
3. Re-encrypt the remaining data with the new key, as the user dcdash runs as:

   ```sh
   sudo -u dcdash dcdash reencrypt
   ```

   Without this step, TOTP secrets are re-encrypted when they are next used.
4. Once all data is re-encrypted, remove the old key from `previous_encryption_keys` and
   destroy it.

Several previous keys can be listed. Keys are identified by a fingerprint stored with each
value, so their order doesn't matter.

## Authentication

### LDAP

Users log in with their directory account (`auth.ldap`). dcdash searches the user with a
read-only service account, then binds as the user on a separate connection to verify the
password.

- **Transport:** `ldaps://`, or `ldap://` with `start_tls: true`. Plain `ldap://` requires
  `insecure: true` and is meant for tests only.
- **Server verification:** the system CAs plus `tls.ca_file`, or a pinned certificate
  fingerprint (`tls.fingerprint`, SHA-256). Pinning suits Samba's autogenerated certificate,
  which has no subject alternative name and therefore fails normal host name verification:

  ```sh
  openssl s_client -connect dc1.example.com:636 </dev/null | openssl x509 -noout -fingerprint -sha256
  ```

  Compare the fingerprint with the certificate on the domain controller
  (`/var/lib/samba/private/tls/cert.pem`) before trusting it. A pin has to be updated when the
  certificate is renewed.
- **Several servers:** with `auth.ldap.servers`, each domain controller can have its own
  fingerprint. A connection fails over to the next server only on network and TLS errors,
  so a certificate that doesn't match moves on to the next server instead of being accepted.
  Directory answers (wrong password, unknown user) are final and never tried on another
  server.
- **Credential handling:**
  - Empty passwords never reach the directory, because LDAP treats them as an anonymous bind,
    which succeeds.
  - Login names are escaped before they're used in search filters.
  - Disabled AD accounts are rejected.
- **Groups:** in AD mode, nested groups are resolved with `LDAP_MATCHING_RULE_IN_CHAIN`. The
  primary group (usually "Domain Users") isn't a `member` relationship in AD, so it isn't
  reported; don't map roles to it.
- **Errors:** unknown users, wrong passwords and disabled accounts all return the same
  response ("invalid username or password").

### Sessions

- The browser receives a random 256-bit token in the cookie `__Host-dcdash_session`, which is
  `Secure`, `HttpOnly` and `SameSite=Strict`. The database stores only the token's SHA-256
  hash.
- A session ends after `auth.session.lifetime` (default 8 hours) or after `idle_timeout`
  (default 8 hours) without requests, whichever comes first. Open pages poll only while they
  are visible, so a tab in the background counts as inactive. Each end of a session is
  logged with its reason. Logging in again always
  creates a new session, so a session can't be fixed in advance (session fixation).
- When a session advances a step (password, then TOTP), its token is replaced.
- A session that has passed the password step but not the TOTP step (or the enrollment)
  expires after 10 minutes. Until then it grants no access.
- An open console (noVNC, terminal, node shell) doesn't count as activity. When the session
  ends, also through the idle timeout, the console is closed within 30 seconds. Someone who
  works only in a console for longer than `idle_timeout` is disconnected; raise the timeout if
  that is a problem.
- Roles are determined from the groups at login. A user removed from a group in the directory
  keeps the session's permissions until it ends; terminate their sessions (see
  [Administration](#administration)) to apply the change right away.

### TOTP

After the password, dcdash asks for a one-time code from an authenticator app (TOTP,
RFC 6238: HMAC-SHA1, 6 digits, 30 seconds), which every common app supports.

**When it's required:** a user must use TOTP if **any** of their roles has `require_totp: true`
(the default). The `root` role and the break-glass account always require it. Users who don't
need TOTP can still enroll voluntarily, and from then on it's enforced for them as well.

**Enrollment:** a user who needs TOTP but hasn't enrolled is asked to enroll right after the
password step. dcdash creates a secret, the app scans it as a QR code, and the user confirms
it with one code. Only then is the secret saved. The user then receives 10 **recovery codes**,
which are shown only once.

**Protection:**

- Secrets are encrypted in the database (see [Data at rest](#data-at-rest)). An enrollment
  in progress is stored encrypted in the session.
- Codes from the previous, current and next 30-second interval are accepted, to allow for
  clock drift. Every code is accepted **only once**; a code that was already used, also the
  one used for enrollment, is rejected.
- After `auth.lockout.totp.max_failures` wrong codes (default 5 in 15 minutes), the user is
  locked out of the TOTP step for the lockout duration.
- Recovery codes (16 characters, about 79 bits) are stored as hashes and work once each. A
  logged-in user can replace all of them with a current code.

**Lost device:** a user can log in with a recovery code. If those are lost too, root resets
the user's TOTP (see [Administration](#administration)), and the user enrolls again at the
next login.

### Administration

| Task | API | Permission |
|---|---|---|
| List active sessions, optionally of one user | `GET /api/v1/admin/sessions?username=` | `system:core:sessions:read` |
| Terminate a session | `DELETE /api/v1/admin/sessions/{id}` | `system:core:sessions:write` |
| Terminate all sessions of a user | `DELETE /api/v1/admin/users/{username}/sessions` | `system:core:sessions:write` |
| Reset a user's TOTP | `DELETE /api/v1/admin/users/{username}/totp` | `root` |

Session lists never contain tokens; sessions are addressed by a separate, non-secret ID.
Resetting a user's TOTP also ends all their sessions, because they may have been started with
the lost device.

On the server, TOTP can also be reset without logging in, for example for the break-glass
account or when no root user can log in:

```sh
sudo -u dcdash dcdash totp reset <username>
```

Every administrative action is recorded in the audit log; actions on the command line use the
operating system user as the actor.

### CSRF protection

State-changing requests must pass three checks:

1. An `Origin` (or `Referer`) header, if present, must match the requested host.
2. Request bodies must be JSON. Cross-site HTML forms can't send JSON without a CORS
   preflight, and dcdash never allows CORS.
3. With a session, the `X-CSRF-Token` header must contain the session's token. It is returned
   by login and `GET /api/v1/auth/me`.

The login request itself is exempt from check 3, because it replaces any existing session.

### Lockout

After `auth.lockout.user.max_failures` failed logins for a user name (default 5 in
15 minutes), or `auth.lockout.ip.max_failures` from one client IP address (default 20), further
attempts are refused with HTTP 429 for the lockout duration. Locked attempts don't reach the
directory, which also protects the AD accounts against the domain's own lockout policy. If
dcdash runs behind a reverse proxy, list the proxy in `server.trusted_proxies`. Otherwise all
clients share the proxy's address.

- Attempts still in progress count against the limit, so parallel requests can't get more
  attempts through than allowed. The same applies to the TOTP step.
- IPv6 clients are counted per /64 network, because a client usually controls the whole /64.
- User names longer than 256 characters or containing control characters are rejected with
  HTTP 400 before they are logged or counted.
- The user lockout counts the name as typed. In AD mode, `jdoe` and `jdoe@example.com` reach
  the same account but are counted separately; the IP lockout still applies to both.

Lockout state is kept in memory and is reset when dcdash restarts.

### Break-glass account

If the directory is unavailable, nobody can log in via LDAP. For this case an optional local
account can be enabled:

```sh
dcdash hash-password > /etc/dcdash/breakglass.hash   # asks for the password (min. 16 characters)
```

```yaml
auth:
  local:
    enabled: true
    username: breakglass
    password_hash: "file:/etc/dcdash/breakglass.hash"
```

- The username is reserved: logins with this name are never sent to the directory. Choose a
  name that doesn't exist there.
- The password is stored as an argon2id hash (64 MiB memory, 3 iterations, 4 lanes).
- The account **always** has to complete the TOTP step. It can't enroll in the web
  interface, so that its password alone never grants access. Enroll it on the server, as the
  user dcdash runs as:

  ```sh
  sudo -u dcdash dcdash totp enroll breakglass
  ```

  The command prints the `otpauth://` URI and the secret, asks for a code, and prints the
  recovery codes. Until then, the account's logins are refused.
- Every use is logged as a warning and recorded in the audit log. The account holds the
  `root` role.

## Roles and permissions

Roles map directory groups to permissions:

```yaml
auth:
  root_group: dashroot          # default
roles:
  - name: dns-operator
    groups: ["dcdash-dns"]      # CN, or a full DN
    require_totp: true          # default
    permissions:
      - "dns:cloudflare-prod:*:write"
      - "dns:bind-internal:*:read"
```

A user holds every role whose groups they're a member of, including nested groups in AD
mode. Group names without `=` are compared with the group's CN. Values with `=` are compared
as DNs. Both comparisons ignore case.

### The root role

Members of `auth.root_group` hold the built-in `root` role. It has every permission
(`*:*:*:admin`) and always requires TOTP. A configured role can't be named `root`, so the
role can't be weakened or removed. The break-glass account always holds `root`.

### Permission format

A permission has four segments, `module:instance:resource:action`:

| Segment | Meaning | Examples |
|---|---|---|
| module | The service family | `proxmox`, `dns`, `dhcp`, `system` |
| instance | A configured backend, by name | `cluster-a`, `cloudflare-prod`; always `core` for `system` |
| resource | An object of the backend | a VM, a zone, a subnet; `audit` or `sessions` for `system` |
| action | The level of access | see below |

The resource may contain colons, for example an IPv6 subnet:
`dhcp:kea:2001:db8::/64:read`.

`*` matches any text, as a whole segment or within one: `dns:*:*.example.com:write` covers
`www.example.com` but not `example.com` itself. Matching is case-sensitive.

Actions are ordered, and a higher action includes all lower ones:

| Action | Allows |
|---|---|
| `read` | Viewing |
| `operate` | Operating without changing configuration, for example starting or stopping a VM |
| `console` | Interactive console access |
| `write` | Creating, changing and deleting |
| `admin` | Everything; `*` as the action means `admin` |

Permissions only grant; there are no deny rules.

### System permissions

| Permission | Allows |
|---|---|
| `system:core:audit:read` | Reading the audit log |
| `system:core:sessions:read` | Listing all sessions |
| `system:core:sessions:write` | Terminating other users' sessions |

Resetting another user's TOTP is reserved for `root`.

### Proxmox permissions

The instance is the cluster name from the configuration. Resources:

| Resource | Object | Actions used |
|---|---|---|
| `qemu/<vmid>` | A virtual machine | `read` (list, details; a template to clone it), `operate` (power actions), `console` (noVNC), `write` (change options, disks and network devices), `admin` (create and delete the VM, delete disks) |
| `lxc/<vmid>` | A container | `read`, `operate`, `console` (terminal), `admin` (create and delete) |
| `node/<name>` | A node | `read` (list, usage); `admin` for the node shell |
| `storage/<node>/<storage>` | A storage | `read` |

Examples: `proxmox:lab:*:read` (everything in cluster `lab`, read-only),
`proxmox:lab:qemu/1*:operate` (power actions on VMs whose ID starts with 1),
`proxmox:*:lxc/*:console` (container terminals in all clusters),
`proxmox:lab:qemu/5*:admin` (create and delete VMs with IDs starting with 5; see
[proxmox.md](proxmox.md#creating-and-deleting-guests)),
`proxmox:lab:qemu/2*:write` (change the hardware of VMs whose ID starts with 2; see
[proxmox.md](proxmox.md#changing-virtual-machines)).

A node shell is a root shell on the hypervisor, so it needs `admin` on the node, not just
`console`. Proxmox checks the privileges of dcdash's API token in addition; see
[proxmox.md](proxmox.md).

### DNS permissions

The instance is the provider name from the configuration, the resource is the zone name
without trailing dot:

| Action | Allows |
|---|---|
| `read` | Listing the zone and its records |
| `write` | Creating, changing and deleting records of the zone |
| `admin` | Creating and deleting the zone |

Examples: `dns:cloudflare-prod:*:read` (all zones of the provider, read-only),
`dns:bind-internal:example.internal:write` (records of one zone),
`dns:bind-internal:*.internal:write` (records of all zones ending in `.internal`),
`dns:*:*:admin` (everything, including zone creation and deletion).

To create a zone, the user needs `admin` on the new zone's name, so a pattern such as
`dns:cloudflare-prod:*.example.com:admin` allows only zones below `example.com`. The
backend's own credentials limit dcdash in addition: the Cloudflare token and the TSIG key's
`update-policy`; see [dns.md](dns.md).

### DHCP permissions

The instance is the server name from the configuration. The resource is the subnet prefix as
Kea reports it, for example `192.0.2.0/24` or `2001:db8:1::/64`, and `global` for global
reservations:

| Action | Allows |
|---|---|
| `read` | Viewing the subnet, its utilization, leases and reservations |
| `operate` | Deleting leases of the subnet |
| `write` | Adding, changing and deleting reservations of the subnet |

Examples: `dhcp:dhcp4-a:*:read` (everything on one server, read-only),
`dhcp:*:192.0.2.0/24:operate` (leases of one subnet on all servers),
`dhcp:dhcp4-a:10.1.*:write` (reservations in all subnets starting with `10.1.`).

Lease searches return only leases of subnets the user may read. Kea's API user can run every
command, so dcdash's permissions are the only restriction per user; see [dhcp.md](dhcp.md).

## Audit log

dcdash records every login attempt and every state-changing action in the audit log, together
with every request that was denied for lack of permission. Each entry contains:

| Field | Content |
|---|---|
| `time` | When it happened (UTC, milliseconds) |
| `actor`, `actorSource` | The user and where they came from (`ldap`, `local`, `cli`, `system`). For failed logins, the name that was given, with source `anonymous` |
| `clientIp` | The client address (see `server.trusted_proxies`) |
| `action` | What happened, for example `auth.login` or `authz.denied` |
| `target` | The object acted on, for example a zone or a user |
| `result` | `success`, `failure` or `denied` |
| `details` | Additional data, for example the reason a login failed |
| `requestId` | The request ID, also found in the application log |

Passwords, TOTP codes and recovery codes are never recorded.

Entries are stored in the database. Users with the permission `system:core:audit:read` can
query them via `GET /api/v1/audit`. Optionally, dcdash also writes every entry as a JSON line
to a file or to syslog (facility `authpriv`), for example to forward it to a SIEM:

```yaml
audit:
  retention: 365d               # 0 keeps entries forever
  file: /var/log/dcdash/audit.log
  syslog:
    enabled: true
    network: udp                # "" for the local syslog daemon
    address: "log.example.com:514"
```

The file is opened for every entry, so it can be rotated without restarting dcdash. If an
entry can't be stored, it is written to the application log as an error instead.

### Recorded actions

| Action | When |
|---|---|
| `auth.login` | Every login attempt. A locked-out attempt has the result `denied` |
| `auth.totp.verify` | Every TOTP or recovery code entered (`details.method`) |
| `auth.totp.enroll` | TOTP enrollment, in the web interface or with `dcdash totp enroll` |
| `auth.recovery_codes.regenerate` | A user replaced their recovery codes |
| `security.reencrypt` | `dcdash reencrypt` |
| `admin.session.terminate` | An administrator terminated sessions; `target` is the user |
| `admin.totp.reset` | TOTP reset in the API or with `dcdash totp reset` |
| `user.preferences.update` | A user saved their preferences (language, theme) |
| `auth.logout` | Logout |
| `authz.denied` | A request was refused for lack of permission; `target` is the missing permission |
| `proxmox.guest.<action>` | A power action (`start`, `shutdown`, `stop`, `reboot`, `suspend`, `resume`); `target` is `<cluster>/<type>/<vmid>`, `details` contain the node and the Proxmox task ID or the error |
| `proxmox.guest.create` | A creation ended; `target` is `<cluster>/<type>/<vmid>`, `result` is its outcome, `details` contain the node, name, source, resources, network, whether a password and how many SSH keys were set (never the password), the Proxmox task IDs and the error |
| `proxmox.guest.delete` | A guest was deleted (the Proxmox task was started); `details` contain the node, name, `purge` and the task ID or the error |
| `proxmox.guest.configure` | Options of a VM were changed, removed or reverted; `details` contain the node, the keys (`set`, `delete`, `revert`, not the values) and the Proxmox task ID or the error |
| `proxmox.disk.create`, `.update`, `.resize`, `.attach`, `.detach`, `.delete` | A disk of a VM was added, changed, grown, attached, detached or deleted; `details` contain the node, the disk key, the volume or storage and size, and the task ID or the error |
| `proxmox.network.create`, `.update`, `.delete` | A network device of a VM was added, changed or removed; `details` contain the node, the device key, the MAC address, bridge and VLAN, and the task ID or the error |
| `proxmox.console.open` | Opening a console or node shell failed (`result` `failure`) |
| `proxmox.console.start`, `proxmox.console.end` | A console session started and ended; `details` contain the duration, the bytes in both directions and why it ended |
| `dns.record.create`, `dns.record.update`, `dns.record.delete` | A record change; `target` is `<provider>/<zone>`, `details` contain name, type, TTL, content and record ID, the previous values for updates (and the error on failure) |
| `dns.zone.create`, `dns.zone.delete` | A zone was created or deleted; `target` is `<provider>/<zone>` |
| `dhcp.lease.delete` | A lease was deleted; `target` is `<server>/<subnet>`, `details` contain the address, MAC address or DUID, host name and the result on each HA partner |
| `dhcp.reservation.create`, `dhcp.reservation.update`, `dhcp.reservation.delete` | A reservation change; `target` is `<server>/<subnet>`, `details` contain the identifier, addresses, host name, the server that stored it, and the previous values for updates |

## Security review

Before v0.1.0, the code was reviewed for authentication, sessions, CSRF, HTTP headers, the
console websocket proxy, input validation and secret handling, and the dependencies were
audited. The continuous integration repeats the dependency audit for every change:
`govulncheck` for Go (reachable code only) and `npm audit` for the frontend, including the
build tools.

Fixed in the review:

- DNS zone and record names allow only letters, digits, `_` and `-` per label. Before, a user
  allowed to create zones below a domain could inject zone options into `rndc addzone`
  (for example to allow dynamic updates from anyone), and a record name could carry a
  different record type into a dynamic update.
- Parallel login or TOTP attempts could exceed the lockout limit (see [Lockout](#lockout)).
- Overlong user names were logged and stored in the audit log before being rejected.
- An open console kept the session from reaching its idle timeout.
- A session could prepare any number of consoles; each starts a proxy process on a Proxmox
  node. Now at most 3 at a time.
- A TOTP reset didn't end the user's sessions.
- The HTTP server had no read and idle timeouts.
- Secret files readable by other users weren't reported.
- DNS record updates didn't record the previous values in the audit log.

Known limitations, accepted for now:

- **Group changes** take effect at the next login (see [Sessions](#sessions)).
- **User enumeration by timing:** the response is the same for unknown and existing users,
  but a wrong password for an existing user takes longer (a second LDAP connection).
- **Lockout per typed name:** see [Lockout](#lockout).
- **Upstream error messages:** errors from Proxmox, Kea and Cloudflare are shown to the user
  who caused them. They can contain details such as node names or storage paths.
- **Fingerprint and CA:** if a TLS fingerprint is set, it replaces the CA check (`ca_file`) for
  that connection; both are not checked together.
- **HSTS behind a proxy:** dcdash sends `Strict-Transport-Security` only on its own TLS
  connections. If a reverse proxy terminates TLS, configure the header there.
- **Concurrent changes:** changes check that the data hasn't changed since it was loaded. For
  bind this check is part of the update itself. For Cloudflare and Kea, a change made by
  someone else in the moment between check and write can be overwritten.
